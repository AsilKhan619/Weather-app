# Interview Notes

Talking points appended at the end of each phase (brief §1, "every phase"): the 3-5 concepts that phase demonstrates, plus two likely interview questions with strong answers.

## Phase 0: Plan and foundation

**Concepts demonstrated:**

1. **Requirements verification before writing code.** Every external API (Open-Meteo's Single Runs / Previous Runs APIs, aviationweather.gov, IEM ASOS) and every pinned library version was checked against current docs before design decisions were finalized — catching one real endpoint correction (IEM's programmatic CGI endpoint vs. its human-facing form) and several version-pin risks (SQLAlchemy 2.1 and httpx 1.0 both still pre-release; ruff 0.16 changed its default rule set ~7x).
2. **KRaft-mode Kafka with no ZooKeeper**, run via the official `apache/kafka` image with combined broker+controller roles — reflects where Kafka operations actually is now (ZooKeeper was fully removed in Kafka 4.0).
3. **SQLAlchemy Core + Alembic migrations without an ORM** — migrations are plain `op.create_table`/`op.execute` calls, not autogenerated from ORM models, which keeps the schema the single source of truth and avoids ORM/migration drift.
4. **Structured JSON logging correlated by `event_id` via a `contextvar`** — lays the groundwork for `make trace` (Phase 3) to walk one event end-to-end through logs, not just data.
5. **Dependency scoping with `uv`'s optional-dependencies/dependency-groups** — Phase 0's environment only installs what Phase 0 needs (Kafka client, Pydantic, SQLAlchemy, Alembic); heavier phase-specific deps (Airflow, Streamlit, pandera) are declared and pinned now but not installed until their phase starts.

**Likely interview questions:**

- *"Why KRaft instead of ZooKeeper for Kafka?"* — ZooKeeper coordination was Kafka's biggest operational pain point (a second distributed system to run and reason about). KRaft moves consensus into Kafka itself via a Raft-based controller quorum, simplifying operations and reducing failure modes. It's been production-ready since Kafka 3.3 (KIP-833) and is now the *only* mode — ZooKeeper support was removed entirely in Kafka 4.0. For a single-broker local project, combined broker+controller roles keep it to one container; production would split those roles and run a real controller quorum.

- *"Why validate the plan against live documentation instead of just building from the spec you were given?"* — Specs and even AI training data go stale, especially for fast-moving projects like Kafka or LLM APIs. In this project that surfaced concretely: the historical-METAR endpoint in the initial design pointed at a human-facing download form rather than the actual programmatic CGI endpoint, which would have failed silently or required rework mid-Phase-2. Catching that during planning — before any ingestion code was written — is much cheaper than catching it after building a backfill CLI against the wrong URL.

## Phase 1: Forecast ingestion slice

**Concepts demonstrated:**

1. **Verifying an external API's actual behavior, not just its docs, before designing around it.** Open-Meteo's Single Runs API docs don't explain how to detect a new model run; a few live `curl` calls made the real contract obvious — requesting an unavailable run returns a clean `HTTP 400 {"error": true}`, distinct from a real failure. That turned "detect a new run" into a simple, testable backwards-scan algorithm instead of a guess.
2. **Idempotency by construction, proven at the database, not just asserted.** Every event's `event_id` is a deterministic hash of its natural key (model, location, run), and every write is `INSERT ... ON CONFLICT DO UPDATE` on that same key. The result: producing and consuming the same run twice is provably a no-op (a real integration test processes the identical Kafka batch twice and asserts the row count doesn't change), while a genuinely new model run correctly adds new rows without touching the old ones — bitemporal storage working as intended, not by accident.
3. **A bug that only a unit test's tiny fixture would hide.** One real micro-batch (15 events × 168 hours × 4 variables = 10,080 rows) blew past Postgres's 65,535-bound-parameter limit on a single multi-row upsert. Unit tests never would have caught this — they use fixtures with a handful of rows. Running the real pipeline against real infrastructure at realistic batch sizes did.
4. **One shared, well-tested primitive instead of two similar-but-different consumer loops.** The bronze sink and silver consumer both need "collect a micro-batch, process it, commit offsets only on success" — that logic lives once (`run_microbatch_loop`), and its restart-safety guarantee is proven directly against it (kill before commit, restart, confirm redelivery; succeed, restart, confirm no redelivery) rather than re-derived per consumer.
5. **Structural typing (`Protocol`) to keep C-extension types testable.** `confluent_kafka.Message` has no public constructor, so it can't be built directly in a test. Typing the streaming code against a `Protocol` capturing only the methods actually used means a plain Python `FakeMessage` satisfies the type checker and lets bronze-sink logic get real, fast unit tests without a broker.

**Likely interview questions:**

- *"How do you know your Kafka consumer won't lose or duplicate data if it crashes mid-batch?"* — Offsets are only committed after the batch's write succeeds (Parquet file written, or DB transaction committed) — never before, never automatically on a timer. If the process dies mid-batch, nothing was committed, so the same messages get redelivered on restart. That alone would cause duplicates on redelivery, except every downstream write is also idempotent (Parquet: a new file each batch, harmless to have twice for bronze's append-only lake; silver: upsert on the natural key). I proved the offset-commit half directly with an integration test that kills a consumer before it commits and confirms a fresh consumer in the same group gets the identical messages back — and proved the idempotency half by processing one batch twice and asserting the row count is unchanged.
- *"Why explode one forecast response into ~672 rows instead of storing it as one row with array columns?"* — The gold layer needs to join each individual (location, model, variable, valid_time) forecast value against the nearest observation via `merge_asof` (Phase 3) — that only works cleanly against a tidy, one-value-per-row table. Storing arrays would just move the explosion into every query that reads the data instead of doing it once at write time.

## Phase 2: Observations and backfill

**The story worth telling from this phase:** the real runs found four problems my tests couldn't - and I measured before fixing. (1) A fresh-clone `.env.example` pointed Kafka at the wrong port and `make up` raced Postgres startup: no test built a `Settings` from the example file, so I added one that pins the example, code defaults and compose ports together (it failed on the old file). (2) The 25-location request came back HTTP 200 with a body truncated mid-JSON at ~692 KB; the API's *size* limit was independent of the *rate* limit I'd designed around, so I batched locations and made a truncated body retryable. (3) The free academic observation archive answered 503 and 429 under load - 6 of 50 requests failed under a default retry; a patient policy turned all 20 transient errors into successes, and I showed that by counting response statuses in both runs rather than assuming it worked. (4) Reconciliation and the observation drain ran at ~130 messages/second; profiling showed ~9 ms of pandas overhead per 4-row message, so per-message work became plain Python with one DataFrame per batch (8.9 ms -> 0.05 ms in a transform-only microbenchmark - I'm careful to say that's not the end-to-end gain).

**Concepts demonstrated:**

1. **Reconciliation as rebuild-equivalence, not a count comparison.** Comparing "produced vs consumed" can't work when identical events are legitimately re-produced every poll and an upsert overwrites the lineage id. Instead the job replays the lake in memory through the *same* silver transform and diffs the resulting set of natural keys against silver, reporting rows missing and rows unexplained separately. `MATCH` means "silver has exactly the rows a rebuild would produce" - it checks keys, not values, and I documented that limit rather than let the name overclaim (value-level equality is covered by a separate rebuild-and-compare integration test).
2. **A subtle comparison bug designed out up front.** pandas builds categoricals and nanosecond timestamps; Postgres returns strings and microsecond timestamps. Comparing naively would flag every row as mismatched. Keys are hashed from a canonical string (timestamps normalised to epoch seconds), and a unit test pins that both representations hash identically.
3. **One load path for live and replay.** The silver consumers' `load_messages` takes anything shaped like a Kafka message (a `Protocol`), so a replay from Parquet runs the exact code the live consumer runs. There is no second implementation of "what silver should contain" to drift out of sync.
4. **Deriving data the source doesn't provide, and being honest about it.** The Previous Runs API gives lead offsets, not run times, so backfilled `init_time` is derived (`valid_time - N days`) and flagged `ingestion_mode='backfill'`. That lets live and historical forecasts share one table and one consumer, at the documented cost that backfilled lead times are day-granular.
5. **Letting the provider's rate-limit model drive the design.** Open-Meteo weights requests by volume (per 10 variables x 14 days x location), so one 7-day, 25-location chunk costs ~35 of a 600/minute, 10,000/day budget. That set the throttle, made a full history a two-day job, and motivated a resumable design (chunk-outer ordering, so a 429 yields an exact `--start-date` to resume from).
6. **Failure modes that only appear under realistic input**, regression-tested: an original METAR and its correction in one micro-batch put the same key twice in one `ON CONFLICT DO UPDATE`, which Postgres rejects; a naive `datetime.timestamp()` silently uses the machine's timezone; and - found by an independent review of the phase, not by me - missing values were stored as `'NaN'::float8` instead of NULL, which would have made every Phase 3 `avg()` NaN, and a truncating rebuild could have destroyed rows that existed only in silver. Both got fixes plus integration tests; the rebuild now refuses to run unless forced.

**Likely interview questions:**

- *"How do you know your warehouse is correct - and that you could rebuild it?"* - Bronze is immutable raw history; silver is derived. `make reconcile` replays bronze through the silver transform in memory and compares natural-key sets to what silver holds, in both directions, so it catches lost rows *and* rows nothing can explain. There's an integration test that truncates both silver tables, rebuilds from a real Parquet lake, and asserts every row - values, flags, lineage ids - is identical; another deletes a row and inserts a phantom one and asserts each is detected and repaired by the right kind of replay (re-apply vs truncate-and-rebuild). What I'd be careful to say in the interview: that proves the mechanism on recorded data; a multi-month run against the live providers is a separate, still-open item.
- *"How do you handle late or corrected data?"* - Keep the natural key free of anything that changes on correction: silver keys observations on `(station, observed_at, variable)`, so a COR simply upserts over the original ("latest version wins") with no delete-then-insert logic. The event id, by contrast, *includes* the raw report text, so a correction is a distinct event with its own bronze record for lineage. Ordering is protected at three levels: a correction outranks its original inside a batch; the upsert itself refuses to let an uncorrected report overwrite a stored correction (my first version only handled the in-batch case, and review caught that a late original in a *later* batch would flip it back); and bronze files are timestamp-prefixed so a replay applies them in write order.

## Phase 3: Gold layer and data quality

**The story worth telling from this phase:** the quality gate, tests and an independent review each found something I had not, and the real providers found one more. (1) While writing the plausible range for pressure I noticed observation pressure was stored in hPa while forecasts are in Pa - a Phase 2 bug the docs said was handled. Every pressure error would have been about -100,000. (2) CI's first run of the new gate quarantined *every* live fixture forecast: I had made "valid time before init time" a blocking check, which was stricter than the data contract, so it became a warning; the same run showed a test that "corrected" a temperature to 99 degC (372 K) - the gate was right and the fixture was wrong. (3) An independent review of the diff found six more (an empty forecast answer crashed the consumer, a config change did not rebuild already-built days, retention plus a late observation would have erased gold history, a duplicated event lost a message, the DLQ reason was generic, old hPa rows would abort gold). (4) On 30 days of real data the hard-range gate quarantined 3 of 27,102 real observations; I checked one against the provider's API - a METAR truncated mid-group (`Q101`) with an altimeter of 2.98 inHg. The bad value is upstream, not a bug of mine.

**Concepts demonstrated:**

1. **Incremental *and* idempotent batch jobs.** Silver only had `inserted_at`, so a revised row was invisible. I added `updated_at`, bumped only when a value differs (`IS DISTINCT FROM`), so a redelivered message changes nothing and a correction advances it. The gold job keeps a watermark, snapshots `now()` before reading (Postgres `now()` is the transaction *start*, so a one-hour lookback covers late commits), and only advances after every day succeeds. A day is *synced*, not appended: upsert what differs, delete keys no longer produced - so re-running leaves both tables identical **including `computed_at`**. I proved that with an MD5 over both tables before and after a re-run on real data.
2. **Deciding what a number means.** `merge_asof` nearest within 30 minutes, NaN observations dropped *before* matching (otherwise the nearest observation could be a NaN and the forecast silently unscored), lead 0 excluded (it is the analysis, not a forecast), whole-day lead buckets (all the backfill can offer), UTC valid dates. Each is a documented choice with a reason, not a default.
3. **Aggregates that compose exactly.** Storing count, bias, MAE and RMSE per day lets the 7/30-day leaderboard be a plain SQL view: `sum(n*mae)/sum(n)` and `sqrt(sum(n*rmse^2)/sum(n))` equal the statistic over the raw errors. A unit test proves it, so the view needs no recomputation.
4. **Data quality with severities that have consequences.** Two schemas per table; which one a check lives in is its severity. Blocking (structure, hard physical limits) quarantines the *message* to the DLQ in silver and aborts the day in gold; warning (plausible range) loads and flags. Two range tiers because unusual weather is real but 500 K is a unit bug. `reconcile` applies the same gate, otherwise every quarantined message would read as data loss and break "silver equals a rebuild from bronze".
5. **Lineage by natural key, not by `source_event_id`.** `source_event_id` names the *latest* writer, so a later event that overwrote rows would make an earlier event look as if it never reached silver. `make trace` recomputes the keys from the bronze payload and reports "N rows still carry this id, M overwritten by event X".
6. **Partitioning with the tradeoffs stated.** Monthly range partitions on `valid_time` because gold and retention both work a date at a time; the primary key already contains it (Postgres requires that). A default partition so an out-of-range row never fails; a job that adopts rows stranded there. Retention is implemented but off by default because the demo *is* the full history, and when on, reconcile compares only the retained window - resolving the tension between retention and "silver is exactly a rebuild" by making the window explicit.
7. **Verifying in the environment that matters.** Local Docker was down all phase, so every Postgres/Kafka behaviour was checked in CI's Testcontainers job and the live-demo workflow. CI caught a partition DDL typo (`FOR VALUES` missing) and an order-dependent test that I would not have seen otherwise.

**Numbers I can defend (real providers, 30 days, 25 locations, GitHub runner):** 1,512,000 forecast + 108,396 observation rows, reconcile `MATCH`; 1,430,440 of 1,440,000 eligible forecast values verified (99.3%); temperature MAE 1.44 K at lead day 1 rising to 2.16 K at day 7 (dew point, wind and pressure also rise monotonically); ICON 1.27 K < ECMWF 1.51 K < GFS 1.55 K for day-1 temperature that month (one window - not a general ranking); silver drain 5 m 45 s for 1.5M rows with the quality gate on (~4,400 rows/s); full gold build 7 m 21 s for 30 days (~15 s/day); quality suite over ~3M rows ~23 s.

**Likely interview questions:**

- *"How do you make a batch job both incremental and idempotent?"* - Two separate mechanisms. Incremental: a change signal that means something (`updated_at` only moves when a value differs), a watermark taken *before* reading and advanced *after* success, a lookback for transactions that commit late, and a rule for which downstream days a change dirties (an observation dirties its day and both neighbours, since a match can straddle midnight). Idempotent: reconcile the day's rows into the table (upsert what differs, delete what is gone) rather than append. The proof is a test that re-runs three ways and compares every column including the compute timestamp, plus the same check on real data. And the watermark's name carries a fingerprint of the matching rules, so changing the tolerance forces a full rebuild instead of mixing rules across days.
- *"What do you do with bad data?"* - Decide per check what a failure *costs*, and encode it. Physically impossible -> the message goes to the DLQ (blocking); merely unusual -> load and flag (warning); in gold, a blocking failure aborts the run rather than skipping the day, because skipping while advancing the watermark would leave that day wrong forever. Every outcome is a row in `ops.quality_results`. On real data this quarantined a truncated METAR from the provider. The honest tradeoff: quarantining by message also drops that hour's good values (3 of 27,102), and a per-variable quarantine would be the refinement.
- *"How would you speed up the gold build?"* - It is the measured bottleneck: ~15 s per day, and a no-op re-run costs the same as a first run because the lookback re-reads and only skips writes. The cost is pandas `to_dict` and row-wise key sets in Python. I would `COPY` the day's frame into a temp table and diff it in SQL, and shrink the lookback window to what late commits actually need. Incremental runs (a few days) are already minutes; I have not measured a full-history build, only extrapolated ~4 hours.
- *"Why partition, and what about retention?"* - ~8M forecast rows a month at full scale, ~50M for the full history. Partition by `valid_time` because every reader and the retention policy work a date at a time; a dropped partition is instant with no vacuum. Retention is off by default and, when on, changes what reconcile compares, because otherwise the intentional deletion looks like data loss. Gold keeps the metrics, the bronze lake keeps the raw events, so a dropped month can be replayed.
- *"What would you do differently?"* - Run the real providers *before* writing the checks rather than after: the pressure unit bug and the negative-lead assumption were both visible in one real response. Add per-variable quarantine. And measure the full-history gold build before claiming a number.

## Phase 4: Streaming alerts and dashboard v1

**The story worth telling from this phase:** the first real run of the detector alerted on sea-level pressure almost exclusively at Bogota, Mexico City and Kathmandu. Rather than raise the thresholds, I looked at why: those stations publish no sea-level pressure in their METARs, so my Phase 2 transform had quietly substituted the *altimeter setting* (QNH) - which is not sea-level pressure at altitude. I confirmed against the live API (Denver reports both: 1014.6 vs 1021.1 hPa at 1,656 m; Bogota's QNH is ~12 hPa above the true value, matching the 1,407 Pa "miss" the detector reported). That same substitution had been silently biasing the gold layer's pressure accuracy at every high station. A monitoring feature found a data bug the accuracy tables had hidden. I fixed the cause (fallback only at stations <= 300 m, pressure otherwise missing) and stopped the detector comparing pressure across sources at altitude. An earlier smaller version of the same lesson: my first live-demo check of "gold re-run changes nothing" failed, and the bug was in my own workflow (the baseline checksum was taken before gold had absorbed the live cycle's new rows), not in the job.

**Concepts demonstrated:**

1. **State that is recoverable because there is none.** The brief asked for small, recoverable detector state. The state a run-to-run comparison needs is already in silver, so the detector reads it on demand (previous run, other models' runs, recent forecasts) and keeps nothing in memory. A restart loses nothing; recovery is "start the consumer". The ADR covers what Kafka Streams or Flink would do instead - keyed state stores with changelog topics and standby replicas, co-partitioning forecasts (keyed by location) with observations (keyed by station), event-time windows and watermarks, transactional exactly-once - and why that machinery is not worth it at ~1,000 events a day.
2. **Exactly-once-ish delivery without transactions.** Alert ids are deterministic (a hash of rule, subject, event time, variable), and delivery is insert -> publish -> mark `published_at` after Kafka confirms. A crash after the insert republishes on restart; an alert already marked is never re-sent; a replayed event produces the same id. Tested with a crash between the steps, and by replaying a recorded event through real Kafka and Postgres (one alert, not two).
3. **Alert design choices with reasons.** Mean rather than maximum over the 48-hour window (one bad hour is noise); absolute differences so opposite swings do not cancel; only live runs alert, because backfilled `init_time` values are derived, not real runs; anything the silver quality gate rejected never alerts; thresholds set relative to measured forecast error and honestly labelled untuned.
4. **A testable dashboard.** Streamlit pages are thin; all reads are plain functions from an engine to DataFrames, integration-tested against Postgres with known numbers (a leaderboard that must rank ICON first, an error curve that must rise with lead). Each page is rendered headlessly with Streamlit's `AppTest` on an empty and a seeded database, and on the real 30-day data in the live-demo workflow. The health page survives Kafka being down. Display units are converted in one place, with a test that an *error* of 2 K is 2 degC and not -271.
5. **Unblocking myself.** Docker was down again, so I ran the Postgres-only integration tests locally against an embedded Postgres (scratch dependency, not added to the project) via an opt-in `NIMBUS_TEST_POSTGRES` setting. That also let me run the migrations up and down for the first time - including the partitioning migration's downgrade, which had been flagged as untested.

**What I can defend from the real run** (14 days of history plus one live cycle, GitHub runner): the detector raised 12 alerts, all published; all four dashboard pages rendered on the real data; the gold re-run checksum was identical. **What I cannot:** the run-to-run change rule has not fired on two real consecutive runs (one cycle gives one run); alert latency on the real path was not measured (the replay test asserts the sub-60-second criterion and prints its measurement in the CI summary); thresholds are untuned; nobody has looked at the dashboard in a browser.

**Likely interview questions:**

- *"How do you keep streaming state recoverable?"* - Prefer not to have any: derive it from a durable store you already maintain. At larger scale use a state store backed by a compacted changelog topic with standby replicas (Kafka Streams) or checkpointed state with offset rewind (Flink), and co-partition the streams on the state key. The tradeoff I chose: a database round trip per event instead of local state - right for hundreds of events a day, wrong for millions.
- *"How do you avoid duplicate or lost alerts?"* - Deterministic ids plus insert-then-publish-then-mark, so both a crash and a replay are safe; a crash between a confirmed delivery and the mark can duplicate one message, so consumers dedupe on the id. Transactions would remove that at the cost of complexity.
- *"Tell me about a time monitoring found a bug."* - The pressure alerts at high-elevation stations: they looked like weather, were actually an unlike-for-like comparison introduced by my own fallback, and the same flaw had biased the accuracy tables. I verified the cause with live data before changing anything, then fixed the source, added regression tests, and documented that pressure is deliberately no longer verified at those stations.
- *"How do you test a dashboard?"* - Put the logic in a query layer and test it against a real database with known numbers; render each page headlessly on an empty and a seeded database; and run the same render on real data in CI. What that does not catch is layout and readability, which I say plainly.
